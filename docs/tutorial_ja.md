# はじめて知識を育てる

[English tutorial](tutorial.md)

このチュートリアルでは、支払い API の短い設計メモを題材に、資料を取り込み、質問し、不足を見つけ、対話を通して育てます。十五分ほどで、Wiki Garden の五つの操作を一通り試せます。

## Step 1. Wiki Garden をセットアップする

最初に、二つの場所を別々に決めます。スキルは「エージェントが Wiki Garden を使えるようにするもの」、知識は「資料や判断を実際に保存するもの」です。

| 選ぶこと | プロジェクトごと | 全体で共有 |
| --- | --- | --- |
| スキルの導入先 | 今いるリポジトリだけで使える | すべてのリポジトリで使える |
| 知識の保存先 | リポジトリ内の `knowledge/` | リポジトリ外の `~/WikiGarden/` など |

この実習では、標準の運用として、スキルを全体へ導入し、知識は `~/WikiGarden/` に共有して保存します。checkout-redesign 固有の設計メモも、共有Wiki内のプロジェクト別の場所へ整理されます。

### スキルを全体へ導入する

```bash
npx skills add hachiware-labs/wiki-garden -g
```

顧客案件など、特定のプロジェクトだけでスキルを使いたい場合は、代わりに `-g` を付けずに導入します。

```bash
npx skills add hachiware-labs/wiki-garden
```

### 知識を共有フォルダーへ保存する

導入した Wiki Garden のスキルに、日本語の知識を共有の `~/WikiGarden/` へ保存するよう頼みます。これは端末で実行するコマンドではなく、エージェントへの依頼です。

```text
複数のプロジェクトで共有する Wiki Garden を初期設定して。
知識は~/WikiGardenに保存し、日本語で記述して。
```

この設定では、`~/wiki-garden.config.md` と `~/WikiGarden/` が使われます。各プロジェクト固有の知識は、共有Wiki内でプロジェクト別に分けて管理されます。

特定業務の知識を独立させたい場合は、代わりに次のように頼みます。

```text
Wiki Garden をこのプロジェクト用に初期設定して。
知識はknowledge/に保存し、日本語で記述して。
```

この場合、設定は `wiki-garden.config.md`、知識は `knowledge/` に保存されます。知識をチームで扱うなら、この二つをリポジトリに含めます。

続けて設定を確認します。

```text
Wiki Garden の設定を診断して。
ファイルは変更せず、保存先と記述言語を確認して。
```

診断結果に、設定元、知識の保存先、記述言語が表示されれば準備完了です。`doctor` はファイルを変更しません。

## Step 2. 資料を取り込む（`ingest`）

`docs/api-notes.md` を作り、次の内容を保存してください。

```markdown
# Checkout API Notes

支払い作成には冪等性キーを使う。
タイムアウトした要求を再試行するときは、同じキーを再利用する。
キーは一回の購入手続きにだけ使い、24時間で失効する。

同じキーを異なる要求本文で再利用すると、現在のAPIはHTTP 409を返す。
この挙動はcheckout-redesignプロジェクト固有であり、別の根拠なしに一般化しない。
```

取り込みを頼みます。

```text
docs/api-notes.md を取り込み、checkout-redesign だけで使う知識として整理して。
原資料も、選んだ知識の保存先の中へ残して。
```

`ingest` は資料をコピーするだけではありません。原資料を残し、資料ごとの要約を作り、再利用できる内容を関連ページへ編み直します。

処理後、次の点を見てください。

- `raw/sources/` から原資料を確認できる
- `sources/` に資料要約がある
- `projects/checkout-redesign/` に日本語の知識がある
- HTTP 409 の挙動が、全体の原則ではなくプロジェクト固有の事実として扱われている

日本語ページに `Summary` や `Status` のような通常語が見出しとして残っていたら、期待した結果ではありません。「要約」「状態」のような日本語で書かれるべきです。

## Step 3. 取り込んだ知識に質問する（`query`）

資料を直接開かず、取り込まれた知識へ質問します。

```text
checkout-redesign の支払い再試行について、今分かっていることを教えて。
```

回答では、同じ冪等性キーを使うこと、キーの適用範囲と有効期間、異なる本文では HTTP 409 になることが説明されるはずです。同時に、HTTP 409 はこのプロジェクトで確認された挙動であり、一般論ではないと分かる必要があります。

`query` は読み取り専用です。答えを作るために Wiki が書き換わってはいけません。

## Step 4. 知識の育てどころを見つける（`lint`）

次に、今ある知識の弱いところを点検します。

```text
checkout-redesign の知識に、矛盾や根拠の弱いところがないか点検して。
問題だけでなく、次に育てる価値がある点も教えて。
```

この例では、プロジェクトの目的がないこと、HTTP 409 を一般化できるか未確認であること、冪等性キーを選んだ理由が弱いことなどが候補になります。

`lint` も読み取り専用です。問題を勝手に直さず、どこを育てるか選べる形で報告します。

## Step 5. 人の判断を加えて知識を育てる（`nurture`）

ここで、プロジェクトの目的が次のように決まったとします。

> タイムアウト時の二重課金を防ぎ、安全に再試行できる API にする。料金計算と画面の再設計は対象外とする。

この判断を既存知識へ結び付けます。

```text
checkout-redesign の目的と対象外を、既存の知識に反映して。
目的は二重課金を防ぎ、安全に再試行できるAPIにすること。
料金計算と画面の再設計は対象外。
外部調査はせず、この判断だけを小さな差分で統合して。
```

期待するのは、`PROJECT.md` など必要なページと履歴だけが更新されることです。原資料や関係のない全体知識まで書き換わるべきではありません。

`nurture` は、既存知識だけで足りなければ人に尋ね、外部の根拠が必要なら範囲を絞って調べます。深く考える場合も、変更は小さく確認できる形にします。

## Step 6. Wiki Garden が見つけた話題を聞く（`what's up`）

最後に、次に話す価値があることを Wiki に準備させます。

```text
最近の履歴、未解決の問い、点検結果から、私と話す価値があるテーマを準備して。
今回は外部調査をせず、正規知識も変更しないで。
```

準備後、自然に尋ねます。

```text
Wiki Garden、何かある？
```

Wiki Garden は一覧ではなく、一つの話題を会話として提示します。この例なら、HTTP 409 の挙動を他の API にも一般化できるか、比較する資料を探すかもしれない、と持ちかけるでしょう。根拠が一件しかなければ、確立した傾向のように語ってはいけません。

興味があれば、その話題を `nurture` します。興味がなければ保留できます。対話のタネは候補であって、正規の事実ではありません。

## 日々の使い分け

すべての操作を毎回使う必要はありません。

- 知りたいときは `query`
- 資料や決まったことを残すときは `ingest`
- 弱いところを探すときは `lint`
- 一つのテーマを育てるときは `nurture`
- Wiki の気づきを聞くときは `what's up`

定期的な処理では、最近の履歴、変更、未解決の問い、点検結果から、少数の対話のタネだけを準備します。問いが明確なら、一つの問いを最大十五分、通常二、三件の信頼できる資料で調べられます。調査しきれなければ「調査待ち」として残します。

最初から大きな Wiki を設計する必要はありません。一つの資料、一つの問い、一つの改善を重ね、未来の自分が読める知識を育ててください。

詳しい決まりは [README](../README_ja.md) と [要件定義](wiki-garden-requirements.md) を参照してください。
